# Draft OpenBEXI Timeline 2.4 implementation prompt

Design OpenBEXI Timeline 2.4 as a simple, friendly application with commercial licensing, model-specific access, and optional AI assistance in the Model and YAML editor. Use the existing README, implementation, schemas, examples, and documentation as the starting point. This is a design and implementation brief; the [Commercial and Exempt Use License](../../../LICENSE) defines the actual licensing terms.

Use the accompanying [HBDS model](./timeline-2.4.hbds.json), [complete model picture](./timeline-2.4.hbds.png), and [overview picture](./timeline-2.4.overview.png) together. Keep them aligned as the design develops. The JSON follows the HBDS v2 document format with `metadata.semanticVersion: 1`, explicit membership, and inheritance. Cardinality annotations and application invariants are proposed domain constraints; the application must implement their enforcement separately from HBDS validation.

**Non-negotiable compatibility rule:** the existing JSON structure and metadata of event, session, and nested activity items must never change. Preserve field names, value types, nesting, null/absent distinctions, existing identifiers, unknown properties, and both supported item representations. Do not inject ownership, roles, license state, AI provenance, HBDS wrappers, or new required fields into items. Keep these relationships in separate model configuration, authorization stores, or external indexes. Existing internal rendering adapters may keep their established behavior, but 2.4 must not migrate or rewrite source items to a new structure. Lock this rule with compatibility fixtures and API/import/export regression tests. It takes precedence over other instructions in this brief.

1. **Commercial licensing and eligibility.** Support commercial agreements and the license's free exemptions for students, noncommercial researchers, charities, nonprofit organizations, and other approved categories. Represent eligibility, verification, entitlement status, expiry, and enabled features explicitly. Keep commercial entitlement separate from authorization: an exemption never grants access to somebody else's model. Entitlement settings do not replace the legal license or verify a purchase. Preserve earlier GPL grants and third-party licenses. Prices and customer-specific scope belong in written commercial agreements.

2. **Users, ownership, and permissions.** Give every model a stable identity and an owning workspace or organization. Users gain access through explicit membership and model role assignments. Every model provides administrator, read/write, and read-only roles; allow additional model-specific roles through explicit permissions. Administrators manage access, model definitions, configuration, and publishing. Only administrators may enter or use the Model and YAML editor, including its AI features. Read/write users manage authorized sessions, events, activities, and permitted filters through normal timeline workflows. Read-only users view, search, and apply permitted filters. Enforce permissions on the server as well as in the interface, including exports, direct document URLs, previews, and AI requests. Distinguish public demonstrations from private models. A model administrator must not acquire control of shared server configuration or unrelated models; shared infrastructure requires separately scoped administration. Prevent removal of a model's last administrator.

3. **One coherent HBDS domain.** Describe every class, typed attribute, identifier, link, inheritance relation, ownership rule, and cardinality in the supplied model. Cover organizations, workspaces, users, memberships, entitlements, models, role definitions and assignments, model versions, YAML/JSON documents and revisions, sources, datasets, filters, sessions, events, activities, AI connections, and generation requests. Keep rendering configuration separate from timeline records and user preferences. Bind model versions to exact document revisions. Define how models reference datasets and sources, including the effect of editing data shared by several models. Each saved filter belongs to one model; define shared and personal visibility, permitted editors, query syntax, sorting, and revision history. Store each user's active filter separately. Migrate existing dataset filters and user/timeline filter files without losing their expressions or sorting.

4. **Compatible data and documents.** Specify representative JSON and YAML examples plus validation schemas. Preserve existing model fields, including `params`, `bands`, `dataSource`, and `rendering`, both model schemas, and supported legacy extensions. Support current source, deployment, and snapshot YAML shapes. Preserve comments, key order where practical, anchors, aliases, and unrelated keys. Retain both legacy `events` with nested `activities` and snapshot `records` with `parentSessionId`; normalize them through explicit adapters. Define session, event, and activity semantics without duplicating records. Preserve stable source identities, metadata, rendering, versions, audit fields, deletions, calendar dates, BCE dates, numeric time axes, uncertainty, and zones. Validate parent references, cycles, dataset boundaries, and time ranges. Never silently reinterpret a populated dataset's time axis. Existing public examples, API routes, and connected source behavior need a documented migration path.

5. **A smaller, clearer editor.** Redesign all editor sections around five understandable areas: Overview, Data, Appearance, Filters, and Access. Keep versions and publishing with Overview. Show YAML/JSON as an Advanced text view of the same draft, with contextual help and searchable properties. Place uncommon settings behind progressive disclosure. Keep the real timeline preview close to the work, responsive on smaller screens, and usable with keyboard navigation. Preserve import, export, duplicate, undo, redo, validation, conflict handling, and the last valid preview. Distinguish draft, saved, published, and restart-required states. Use concise labels, useful defaults, and inline errors. Keep Timeline, Table, Split, 2D/3D, overview, search, and existing rendering options available without filling the screen with controls.

6. **Optional AI that fits the workflow.** Provide one internal AI interface with provider adapters for OpenAI, Anthropic Claude, Hugging Face inference services, and future hosted or local providers. Discover or configure capabilities such as vision, structured output, streaming, context limits, and availability; do not assume all providers or models offer identical features. Keep provider models distinct from timeline models. AI should explain configuration, suggest valid changes, repair drafts, and help create models across existing and future application modes. Let an administrator drop a timeline image and receive an editable rendering proposal covering layout, bands, colors, labels, and grouping. Clearly identify inferred or unreadable details; do not invent factual sessions or events from an image. Show proposed changes and a live preview before applying them. Support undo, cancellation, clear failures, and continued manual editing. Keep credentials server-side, apply permission checks and usage limits, and make the selected provider and submitted content clear.

7. **Delivery and verification.** Begin with a gap analysis against the current application, then implement in reviewable stages with explicit migrations. Test role isolation, shared-data boundaries, model-owned filters, document preservation, concurrent edits, data compatibility, AI capability fallbacks, image proposals, and accessibility. Reuse existing schema, API, and browser checks. Keep the README focused on getting started and link to detailed 2.4 guides. Finish with the updated HBDS artifacts, working examples, editor workflows, test results, and clearly identified unresolved product decisions.
